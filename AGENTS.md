# AGENTS.md

This file provides guidance to coding agents when working with code in this repository.

## Commands

```sh
npm run build        # tsc to dist/ + mark the CLI entrypoint executable (via node, so it works cross-platform)
npm run build:skill  # Regenerate skills/sentry-axi/SKILL.md from shared CLI guidance and SDK built-ins
npm run dev          # Run the CLI from source with tsx
npm test             # vitest run --dir test (unit suite, no network needed)
npm run test:watch   # vitest watch mode
npm run test:e2e     # live suite - needs SENTRY_AUTH_TOKEN + a real org/project; runs files serially
```

Run a single test file: `npm test -- test/render.test.ts`.
Filter by test name: `npm test -- -t "parseNextCursor"`.

The committed `skills/sentry-axi/SKILL.md` is generated by `npm run build:skill`; `npx tsx scripts/build-skill.ts --check` fails if it drifts.
Update the generator (`src/skill.ts`) instead of hand-editing `SKILL.md`.
`package.json` includes `skills/sentry-axi/` in `files`, so npm releases ship the generated installable Agent Skill.

The benchmark harness is a separate package under `bench/` (own `package.json`): `cd bench && npm run bench -- <run|matrix|report>`, `npx vitest run test` for its unit tests.

## Project Conventions

- Node 20+, TypeScript, ESM-only (`"type": "module"`, module resolution `Node16` - relative imports use `.js` extensions even from `.ts` files).
- Unit tests live in `test/*.test.ts`; live e2e tests in `e2e/*.e2e.test.ts` (gated: they skip when `SENTRY_AUTH_TOKEN` is absent). Both run with Vitest.
- Run `npm run build` and `npm test` before pushing.
- Do not hand-edit generated files: `skills/sentry-axi/SKILL.md` (owned by `build:skill`).
- Captured Sentry API response formats live in `test/fixtures/api-responses.md` - parsers are written against those exact shapes; when Sentry changes a format, re-capture and update the fixture and its tests together.

## Architecture

sentry-axi is an agent-ergonomic CLI for triaging Sentry errors, architecturally a sibling of [flutter-axi](https://github.com/ammar00sheikh/flutter-axi) and [chrome-devtools-axi](https://github.com/kunchenguid/chrome-devtools-axi).
Every invocation is a short-lived process.

### Process model: there isn't one

This is the load-bearing difference from its siblings, and the first thing to understand before porting any pattern across.

flutter-axi and chrome-devtools-axi both run a **detached bridge process** that holds a persistent MCP stdio session, because the thing they drive (a running Flutter app, a browser tab) is long-lived and stateful, and an MCP server is a child process that cannot survive between CLI invocations.

Sentry is a stateless HTTPS API. There is nothing to keep alive. So sentry-axi has **no bridge, no ports, no PID files, no health checks, and no teardown** - `src/api.ts` is the entire backend, and a command is: resolve config -> one or two `fetch` calls -> render -> exit.

If you find yourself porting `bridge.ts` or `client.ts` from a sibling repo, stop; the complexity they exist to manage does not exist here.

### Config resolution (`src/config.ts`)

sentry-axi deliberately reads the **same config files the official `sentry-cli` already uses** (`.sentryclirc`, `sentry.properties`), so a repo already set up for Sentry needs zero sentry-axi configuration.

Precedence, highest first:

- **token** - `SENTRY_AUTH_TOKEN` > `SENTRY_AXI_TOKEN` > `~/.sentry-axi/auth.json` (written by `login`) > `./.sentryclirc` > `~/.sentryclirc`
- **url** - `SENTRY_AXI_URL` > `SENTRY_URL` > `.sentryclirc` > `https://sentry.io`
- **scope** - `--org`/`--project` > `SENTRY_ORG`/`SENTRY_PROJECT` > the session's `scope.json` (written by `use`) > `.sentryclirc` > `sentry.properties`

`--session`, `--org`, and `--project` are extracted from anywhere in argv (`extractGlobalFlags`) and exported as the environment variables the config layer already reads, so downstream modules need zero plumbing - the same trick flutter-axi plays with `--app`.

The parsers are pure and exported, so the exact file shapes are unit-tested without touching the filesystem.
`doctor` prints the resolved values **and where each came from**; it is the first command to reach for when something talks to the wrong org.

### Errors (`src/errors.ts`, `errorForStatus` in `src/api.ts`)

Every failure surfaces as a `SentryAxiError` (extends `AxiError`) with a stable code and at least one recovery suggestion: `AUTH_REQUIRED | AUTH_INVALID | NO_PROJECT | NOT_FOUND | REF_NOT_FOUND | STALE_REF | RATE_LIMITED | API_ERROR | NETWORK_ERROR | TIMEOUT | SEER_UNAVAILABLE | TOOLCHAIN_MISSING | VALIDATION_ERROR | UNKNOWN`.

`errorForStatus` is the single chokepoint where an HTTP status becomes agent-actionable (401 -> re-login, 403 -> the missing scopes by name, 429 -> the actual Retry-After delay, 5xx -> retry).
`extractApiMessage` handles Sentry's four different error-body shapes and **refuses to echo an HTML error page** - a 401 can return a login page, and dumping markup at an agent burns context and says nothing.

**Argument validation runs before auth resolution.** Otherwise a typo'd `--limit abc` on an unauthenticated machine reports `AUTH_REQUIRED`, and the agent goes and fixes the wrong thing.

`formatError` (in `src/cli.ts`) overrides the SDK's default error renderer, which would TOON-encode `help` into one comma-separated line. Suggestions are commands an agent copies back verbatim, so they must be one per line, and errors must not have a different output shape than successes.

### Refs: uid -> entity registry (`src/refs.ts`)

Listing commands mint generation-stamped uids (`@g3:12`) and persist what each points at in `refs.json`, so action commands in later short-lived processes translate a uid back to a Sentry id without the agent ever echoing a 19-digit issue id.

**These refs deliberately do not go stale the way flutter-axi's do**, and this is the one place a naive port would be actively wrong.
flutter-axi wipes its registry on every snapshot and hard-fails older refs with `STALE_REF`, because its refs resolve to *positional widget finders* - the tree re-renders, and the widget at that finder may now be a different button. Acting on a stale one is dangerous.
Sentry refs resolve to *immutable entity ids*: `@g1:3` -> issue `4509` means issue 4509 forever, and re-running `issues` cannot make it point elsewhere. Hard-failing it would force a pointless re-listing before every `resolve` - exactly the chattiness an AXI exists to remove.

So the registry **accumulates** and retains the last `RETAINED_GENERATIONS` (5). A ref older than the window is pruned and reports `STALE_REF`, which is a real signal ("that listing is long gone") rather than a safety trip. An unknown uid is `REF_NOT_FOUND`.

The escape hatch mirrors flutter-axi's finder strings: `short:FRONTEND-4F`, `id:4509172`, or a pasted Sentry issue URL bypass the registry entirely (`parseIdentifier`). Agents paste short ids out of alert emails constantly, and that must not require a listing first.

### Rendering: where the token savings actually are (`src/render.ts`)

A single Sentry event payload is routinely 50-200KB of JSON - every frame carries `vars`, source `context`, module paths, and a dozen redundant id fields. Handing that to an agent is what makes raw-MCP Sentry access expensive. Two decisions do most of the work:

- **Frames are reversed.** Sentry stores `stacktrace.frames` oldest-caller-first, so the frame that actually threw is **last**. Agents read the first line as the culprit. Getting this backwards is the most damaging bug possible here: the agent goes and edits `react-dom`. The exception chain in `entries[type=exception].data.values` is likewise cause-first, so it is reversed too.
- **Library frames are collapsed.** A React stack is 90% `node_modules` frames nobody can fix. In-app frames print in full; consecutive non-app runs collapse to `... N library frames`. `--full` disables it, `--context` adds source lines for the crashing frame only.

TOON's tabular array encoding does the rest: `issues[25]{uid,shortId,level,events,users,age,title}:` states the field names once instead of repeating them on every row as JSON does.

Everything in this module is a pure function over parsed JSON, unit-tested against `test/fixtures/api-responses.md` with no network.

### Seer (`src/seer.ts`)

`POST /issues/{id}/autofix/` starts a run; `GET` on the same path polls it. A run takes tens of seconds, so `seer` starts it (or picks up an existing one) and polls to completion - the agent issues one command instead of writing a poll loop. `sleep` and `now` are injectable so the loop is testable without waiting.

Seer's step payloads are **the least stable shape in the Sentry API** - steps get renamed and re-typed, and prose lands under `causes` / `insights` / `solution` / `description`, holding either strings or objects keyed `markdown` / `description` / `title` / `insight`. `extractInsights` therefore walks defensively rather than matching a schema: a shape change **degrades** the output, it does not throw.

### The sentry-cli delegation layer (`src/sentrycli.ts`)

Sourcemap and debug-file uploads go through Sentry's **chunked upload protocol** (blake3 hashing, chunk negotiation against `/chunk-upload/`, assemble polling). Reimplementing that would be a large pile of subtly-wrong code whose failure mode is silently-broken sourcemaps in production.

The official `sentry-cli` already implements it, so sentry-axi treats it as a **toolchain dependency** - exactly what flutter-axi does with `adb` / `xcrun simctl`.
Everything above the executors is a **pure command builder** returning exact argv, so the full flag matrix is unit-testable with no `sentry-cli` installed on any platform. A missing binary is a structured `TOOLCHAIN_MISSING` with install instructions, never a raw ENOENT.

`buildEnv` passes the **already-resolved** token/url/org/project to the child rather than letting it re-discover its own, so it can never end up pointed at a different org than the rest of the session.

`sourcemaps upload` defaults to `--strict`: uploading zero files is the single most common cause of unminified traces in production, so it must be a loud failure, not a silent success.

### Output (`src/output.ts`, `src/suggestions.ts`)

Per command: a TOON metadata block, optional free-text blocks (stack traces, Seer prose - things a table would mangle), then a `help[N]:` block of contextual next steps.
Suggestions are not generic docs - they carry the actual uids just printed, so the agent copies back the exact printed form. The ordering encodes the triage loop: `issues` -> `stacktrace` -> `seer`/`suspect` -> `resolve`.
Every branch returns at least one suggestion, including the empty-result branch, which suggests **widening the window** rather than letting the agent conclude there is nothing to find.

## Things to know when editing

- `handleHome` must stay **cheap and side-effect free**: it mints no refs and bumps no generation. It is what the SessionStart hook runs, and a hook that silently invalidated the agent's refs on every session start would be maddening to debug. It also renders guidance rather than an error when unconfigured, because an error is a terrible first thing for an agent to see.
- Mutations must be idempotent (repeat = no-op success). Sentry's issue `PUT` is a set-to-state, not a toggle, so this holds by construction - keep it that way.
- `resolveOutputPath` (`src/paths.ts`) is the chokepoint for caller-supplied output paths.
- Session names are validated at the single chokepoint `resolveSessionName`, including the dots-only case (`.`, `..`) which would otherwise collapse a named session's state dir onto the default session's.
- New commands must follow the AXI checklist: a per-command `--help` entry in `COMMAND_HELP`, TOON output, a structured `SentryAxiError` with suggestions on every failure path, idempotent mutations, `--session`/`--org`/`--project` compatibility, and a `test/` case for argument parsing.
- e2e suites are gated on `SENTRY_AUTH_TOKEN` and must stay skippable, so `npm test` and CI never need a real Sentry org.
